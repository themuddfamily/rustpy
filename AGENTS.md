# Guidance for AI coding agents and automation

These rules apply to any automated contributor (coding agents, scripts, bots) working in this
repository. Human contributors should read [docs/contributing.md](docs/contributing.md); the
same conventions apply here, plus the rules below.

## Resource limits

RustPy is a large workspace and is often built on shared machines.

- Cap every level of parallelism: at most two CPU cores, two Cargo jobs, two Rayon workers and
  two Rust test threads, at reduced priority. Cargo's job limit alone does not limit test
  threads or Rayon pools. Set the CPU affinity so child processes inherit it:
  ```sh
  export CARGO_BUILD_JOBS=2 RAYON_NUM_THREADS=2 RUST_TEST_THREADS=2
  nice -n 10 taskset -c 0,1 cargo test -j 2 --workspace -- --test-threads=2
  ```
  `python3 scripts/quality.py <gate> --execute` applies these limits for you on Linux. Use
  higher limits only when the machine's owner has said so.
- Run one build or test job at a time. Never start Cargo builds in several checkouts or
  worktrees in parallel; they compete for CPU, memory and the build cache.
- Do not run benchmarks, the performance driver or other long workloads unless they are the
  task.

## Worktrees and temporary files

- When working in parallel on separate features, use one linked Git worktree per task, with
  disjoint file ownership. Share the repository's Git objects and one Cargo target directory
  (`CARGO_TARGET_DIR`); do not copy `target/`, caches or dependency directories into a worktree.
- Put temporary files, test projects and smoke-test configuration in one dedicated temporary
  directory for the task (set `TMPDIR` to it) instead of scattering new directories across the
  system temporary folder. Remove what you created when you are done.
- Remove worktrees you created once their branch is merged, after checking that nothing
  uncommitted or unpushed would be lost.

## GUI and external effects

- Never open windows on the user's desktop. Run the IDE only through `scripts/smoke.sh`, which
  uses a private Xvfb display, with a fresh `RUSTPY_CONFIG_DIR`.
- Do not use the user's real IDE settings, credentials, keyring or SSH keys in tests.
- Do not install system packages, push, tag, publish releases or enable CI workflows unless the
  task explicitly asks for it.

## Commits

- Commit only the files you own for the task, by explicit path. Never use `git add -A` or
  `git add .`, and never commit generated build output, logs or local paths.
- Do not modify third-party or generated content by hand: `vendor/`,
  `crates/rustpy-semantic/typeshed/`, `THIRD-PARTY-NOTICES.txt`,
  `packaging/CARGO-THIRD-PARTY-NOTICES.txt` and the lockfiles are regenerated by their tools.
- Write commit messages that describe the change for a reader of the history; keep process
  notes, machine paths and tool transcripts out of commits, comments and documentation.
- Keep the code rustfmt-clean and Clippy-clean (`-D warnings`).

## Verify before claiming

- Only report a check as passing if you ran it on the current source and saw it pass. A test
  that exists but was not run is not evidence; say what you did not run.
- Add regression tests with each fix or feature (see the fixture guidance in
  [docs/contributing.md](docs/contributing.md#tests-and-fixtures)).
- Mark a roadmap item `[x]` only when it is implemented and verified; otherwise keep it `[~]`
  with a short note of what is missing. Record user-visible changes in
  [CHANGELOG.md](CHANGELOG.md).
- Keep reports short: what changed, what was checked, what remains.
