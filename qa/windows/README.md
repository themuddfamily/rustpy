# Windows acceptance packs

Hand-run checks of RustPy's Windows-only behaviour on a real Windows 10/11 host.
Each pack is a folder with cross-built helper executables and a PowerShell
script. The script computes the expected answer from Windows itself (registry,
`py`, the browsers, Windows Installer), runs RustPy's real code through the
helpers, prints `PASS`/`FAIL`/`SKIP` lines and saves a summary and a JSON
report next to itself. Nothing persistent changes outside the script's own
temporary folder, which is deleted at the end.

Run from a normal (non-admin) PowerShell window in the pack folder.

## Pack 1: interpreter discovery

`run-windows-acceptance.ps1` + `windows_acceptance.exe`
(`crates/rustpy-project/examples/windows_acceptance.rs`): Windows registry
(PEP 514), `py` launcher and WSL distribution discovery and probing.

    powershell -ExecutionPolicy Bypass -File .\run-windows-acceptance.ps1

## Chromium launch diagnostic

Files: `run-chromium-diagnostic.ps1`, `windows_chromium_diagnostic.exe`
(`crates/rustpy-ui/examples/windows_chromium_diagnostic.rs`); assembled alone
by `qa/windows/assemble-chromium-diagnostic.sh <dir>` and also part of pack 2.

    powershell -ExecutionPolicy Bypass -File .\run-chromium-diagnostic.ps1

Launches Edge and Chrome headless (throw-away profiles under `%TEMP%`) in
several ways: plain `CreateProcess` without a job (also with
`--do-not-de-elevate` and with the ConPTY `TERM` variables), the external-tool
`ProcessOwner` job, the Run tool's Program session with and without
"Emulate terminal" (ConPTY), kill-on-close jobs with and without
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` that survive the first process's exit, and the
launcher session that Open in browser / Open URL use. For each it records the
page request and JavaScript beacon, the first process's exit code and time,
every process of the run (by parent and by profile folder) with its job
membership, and the tail of `chrome_debug.log`; everything is ended
afterwards. `-Browsers edge`, `-Modes plain,launcher`, `-Timeout 30` and
`-KeepTemp` narrow or extend it. Send back `chromium-diagnostic-summary.txt`
and `chromium-diagnostic-report.json`.

## Pack 2: Add Interpreter flows, Web Browsers and Preview, MSI

Files: `run-windows-acceptance-2.ps1`, `run-chromium-diagnostic.ps1`, `windows_interpreter_acceptance.exe`
(`crates/rustpy-project/examples/windows_interpreter_acceptance.rs`),
`windows_browser_acceptance.exe`
(`crates/rustpy-ui/examples/windows_browser_acceptance.rs`),
`windows_chromium_diagnostic.exe`, the release
`rustpy.exe` (its PDB only with `INCLUDE_PDB=1`), `rustpy.wxs`, `THIRD-PARTY-NOTICES.txt`,
`pack-info.txt`.

    powershell -ExecutionPolicy Bypass -File .\run-windows-acceptance-2.ps1
    powershell -ExecutionPolicy Bypass -File .\run-windows-acceptance-2.ps1 -Gui -Distro Ubuntu

| Option | Effect |
| --- | --- |
| `-Python C:\Python314\python.exe` | base interpreter for new environments (default: that path when it exists, else the `py` default) |
| `-Distro <name>` | also add the WSL distribution's `python3` through Add Interpreter › WSL |
| `-Gui` | also open the real RustPy window for about 20 seconds (it closes itself) to check the WebView2 built-in preview |
| `-SkipMsiInstall` | build and validate the MSI, do not install it |
| `-KeepTemp` | keep the temporary folder |

Send back `windows-acceptance-2-summary.txt` (and `windows-acceptance-2-report.json`).

### What it checks

1. **Add Interpreter** (everything through `environment_manager::Task`, the
   backend of the dialog's Create / Select / Reload buttons, and its
   `Registry` catalogue):
   Virtualenv › New with "install requirements" (an offline wheel generated by
   the helper) in a project folder whose name has a space and a non-ASCII
   letter; `Scripts\python.exe`, `pyvenv.cfg`, the installed package, `pip
   --version` and `pip show` checked by running the new environment's Python
   directly; Virtualenv › Existing; every discovered system Python selected
   as an existing interpreter (version compared with the interpreter's own
   answer); the `py` launcher as the base interpreter; "Inherit global
   site-packages"; refusal of an existing location; a missing base
   interpreter; Cancel while `python -m venv` runs (no process left); uv ›
   New when `uv` is on PATH; WSL with `-Distro`; naming, project
   association, project SDK, rename and "Remove from configured list" in an
   isolated catalogue (your own `%APPDATA%\rustpy` is checked to be untouched).
2. **Web Browsers and Preview**: Edge/Chrome/Firefox detection compared with
   App Paths (HKCU/HKLM) and the install folders; "Open in browser": the
   real preview host serves a page that each installed browser loads headless
   through RustPy's launch planner and launcher Run session (the page's JavaScript and
   stylesheet report back to a local listener); Stop ends the browser's
   process tree; Open URL passes an address with spaces and an option-like
   query as one argument; refused URLs; with `-Gui`, the real `rustpy.exe`
   opens the page in the WebView2 built-in preview
   (`--action WebPreview.Open`), the page reports back with an Edge WebView2
   user agent, and WebView2's data stays in RustPy's system folder.
3. **MSI**: when `wix` is installed, builds the MSI from `rustpy.wxs` and the
   shipped `rustpy.exe` with the `WixToolset.UI.wixext` extension (a global
   copy matching the WiX version, otherwise `wix extension add` into the
   temporary folder only), runs ICE validation (`wix msi validate`), inspects
   the package tables through Windows Installer (per-user, associations,
   shortcut, the `Core` / `FileAssociations` / `ContextMenu` / `AddToPath`
   features, their `ASSOCIATE_FILES` / `CONTEXT_MENU` / `ADD_TO_PATH`
   conditions, which feature owns each resource, the feature-tree dialog).
   It then installs it per user into the temporary folder with
   `ASSOCIATE_FILES=0 CONTEXT_MENU=0`, checks rustpy.exe, the Start menu
   shortcut, PATH and the feature states, that your `HKCU\Software\Classes`
   `.py`/`.pyi`/`.ipynb` keys (default values and all subkeys) are unchanged
   and that no RustPy ProgId or context-menu entry was added, uninstalls it
   and checks everything is removed and the `.py` keys are identical to
   before. A second, full install (associations and context menu on) runs
   only when no per-user `.py`/`.pyi`/`.ipynb` association exists; both are
   skipped (with the manual command printed) when a RustPy installation
   already exists. An aborted run uninstalls the test MSI. Without WiX it
   prints SKIP and the install command:

       dotnet tool install --global wix --version 5.0.2

   (needs the .NET SDK: `winget install Microsoft.DotNet.SDK.8`).

## MSIX pack: Microsoft Store package

Files: `run-msix-acceptance.ps1`, `rustpy-<version>-windows-x64-test-signed.msix`,
`rustpy-msix-test.cer` (the throw-away self-signed certificate the package is
signed with; its subject is the manifest Publisher), `README.md`, `pack-info.txt`.

    powershell -ExecutionPolicy Bypass -File .\run-msix-acceptance.ps1
    powershell -ExecutionPolicy Bypass -File .\run-msix-acceptance.ps1 -Gui

| Option | Effect |
| --- | --- |
| `-Gui` | also open the real RustPy window through the package for a few seconds (screenshot, then it closes itself) |
| `-MachineCert` | trust the certificate in `LocalMachine\TrustedPeople` (elevated PowerShell) when Windows rejects it from `CurrentUser\TrustedPeople` with 0x800B0109 |
| `-KeepInstalled` | leave the package and the certificate installed for manual checks (the removal commands are printed) |
| `-Package <path>` | test another `.msix` |

Sideloading a package needs its signer to be trusted. The script imports the
test certificate into `CurrentUser\TrustedPeople` (never into a root store),
installs the package for the current user with `Add-AppxPackage`, checks
`Get-AppxPackage` (version, status, `WindowsApps` location), the manifest as
Windows registered it (`.py`/`.pyi`/`.ipynb` file type associations, the
`rustpy.exe` app execution alias, `runFullTrust`), that `Get-Command rustpy`
finds the alias in `%LOCALAPPDATA%\Microsoft\WindowsApps`, and runs
`rustpy --verbose --version` through the alias: it must print
`install: msix`, `package-identity: yes` and `updates: Microsoft Store`
(RustPy's own updater is off in Store installs). It then removes the package
and the certificate, checks the alias is gone and that the default values of
your `HKCU\Software\Classes\.py`/`.pyi`/`.ipynb` keys and the Explorer
`UserChoice` keys are identical to before (a package only offers RustPy in
"Open with" and Settings › Apps › Default apps). It refuses to run when a
package with the same identity name is already installed. Send back
`msix-acceptance-summary.txt` (and `msix-acceptance-report.json`).

### Building the pack (Linux/WSL)

    qa/windows/assemble-msix-pack.sh <output dir>          # x64; add arm64 for arm64

It cross-builds `rustpy.exe` with cargo-xwin, packs it with makemsix
(`packaging/windows/build-msix.sh --sign`; `BUILD_MAKEMSIX=1` builds makemsix
first) and signs a copy with osslsigncode. Never run the Windows executables
from WSL; copy the folder to Windows.
